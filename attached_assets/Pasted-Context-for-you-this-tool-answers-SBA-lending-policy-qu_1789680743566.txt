The following defects remain. Work them in order.

Validate every numeric and threshold comparison before rendering. The last run printed "The Buyer has 32 percent directly, which is less than 20%," which is false, and then built a conclusion on it. Any proposition containing a percentage, dollar amount, or comparison operator must pass a deterministic arithmetic check, computed in code rather than generated as text. If the check fails, suppress the proposition rather than printing it.
Separate the applied conclusion from the quoted rule. Right now most propositions are verbatim copies of the retrieved quote, which makes the entailment check a tautology and the SUPPORTS THIS CONCLUSION badge uninformative. Restructure each sub-question as a short applied conclusion in the tool's own words, stating the answer against the user's facts, followed by the supporting propositions and citations. Run the entailment check against the applied conclusion, not against a restatement of the quote.
Confirm the entailment check can return negative. Every badge in the last run was affirmative, including one attached to an inapplicable provision. Construct adversarial pairs where the citation does not support the conclusion, verify the check fires negative, and render an explicit not-supported state in the UI. A check that has never failed is a decorative label.
Distinguish no provision in source from retrieval returned nothing. The last run reported "no provision located" for the seller note question, which is wrong. The SOP addresses seller financing, equity injection sources, and standby treatment. Two fixes. First, generate sub-questions in SOP vocabulary rather than open-ended phrasing, so "what are the implications of the seller taking back a note" becomes a query against terms like equity injection, acceptable sources of injection, seller financing, standby, subordinated debt. Second, when retrieval returns nothing above threshold, say that retrieval found no responsive provision and name the terms searched, rather than asserting the SOP is silent.
Answer the question actually asked. The first sub-question asked whether ROBS funds count toward the equity injection, and the output returned only the eligibility rule for businesses partly owned by a 401(k) plan. An injection answer must state the minimum required injection for the transaction type, compute it against the stated purchase price or loan amount, identify acceptable sources, and list the verification and documentation the lender must obtain and when. Route injection questions to the equity injection provisions, not only to the topical chapter where the funding mechanism is described.
Enumerate guarantors by party and capacity. When more than one owner crosses the ownership threshold, or when an entity or trust holds an interest, the output must list each required guarantor individually, the capacity in which each signs, the provision that triggers each obligation, and any additional requirements that attach when a trust provides the guaranty. In the last run the trust guaranty language appeared inside a context window and was never promoted to a proposition.
Deduplicate citations across sections and add an answer summary. The same page 47 and page 93 passages appeared two and three times, so the output reads like a citator rather than an answer. Show each passage once, reference it by page thereafter, and open the answer with a two or three sentence summary of the bottom line across all sub-questions.

When the user names a different SOP version in the query, state plainly that the answer comes from 8.1 and that the cited provisions take effect October 1, 2026.
